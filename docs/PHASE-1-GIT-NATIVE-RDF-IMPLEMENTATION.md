# Phase 1: Git-Native I/O RDF Refactoring Implementation Plan

**Version:** 3.0.0-alpha
**Target Duration:** Weeks 1-4 (28 days)
**Priority:** CRITICAL (foundational to all operations)
**Expected Outcome:** Proof of concept demonstrating 10x deadlock prevention capability

---

## Executive Summary

Phase 1 refactors GitVan's Git-Native I/O subsystem from JSON-based storage to RDF-backed semantic state management. This foundation enables:

- **Semantic Deadlock Detection** - Query circular lock dependencies with SPARQL
- **Advanced Lock Analytics** - Duration analysis, resource contention patterns
- **Snapshot Provenance** - Full audit trail of state evolution
- **Queue Reasoning** - Automatic dependency resolution

**Current State:**
- LockManager: JSON blobs in Git refs (atomic but non-queryable)
- SnapshotStore: JSON files with SHA-256 hashing (efficient but not semantic)
- QueueManager: In-memory/Git-backed (simple but limited analysis)

**Target State:**
- LockManager: RDF triples with lock graph (queryable + atomic)
- SnapshotStore: RDF with PROV-O provenance (queryable + auditable)
- QueueManager: RDF DAG with dependencies (queryable + reasoning)

### Task 1.1: Define Lock Ontology (Days 1-2)

**File:** `src/rdf/ontologies/lock-ontology.ttl`

**Turtle Schema:**

```turtle
@prefix lock: <https://gitvan.dev/lock#> .
@prefix xsd: <http://www.w3.org/2001/XMLSchema#> .
@prefix rdf: <http://www.w3.org/1999/02/22-rdf-syntax-ns#> .
@prefix rdfs: <http://www.w3.org/2000/01/rdf-schema#> .
@prefix prov: <http://www.w3.org/ns/prov#> .

# Lock class
lock:Lock a rdfs:Class ;
  rdfs:label "Distributed Lock" ;
  rdfs:comment "A named lock acquired for mutual exclusion of resources" .

lock:lockId a rdf:Property ;
  rdfs:domain lock:Lock ;
  rdfs:range xsd:string ;
  rdfs:label "Lock Identifier" ;
  rdfs:comment "Unique UUID identifying this lock instance" .

lock:resourceId a rdf:Property ;
  rdfs:domain lock:Lock ;
  rdfs:range xsd:string ;
  rdfs:label "Resource Identifier" ;
  rdfs:comment "URI or identifier of the locked resource" .

lock:owner a rdf:Property ;
  rdfs:domain lock:Lock ;
  rdfs:range xsd:string ;
  rdfs:label "Lock Owner" ;
  rdfs:comment "Process ID, hostname, or user that holds the lock" .

lock:acquiredAt a rdf:Property ;
  rdfs:domain lock:Lock ;
  rdfs:range xsd:dateTime ;
  rdfs:label "Acquisition Time" ;
  rdfs:comment "When the lock was acquired (ISO 8601)" .

lock:expiresAt a rdf:Property ;
  rdfs:domain lock:Lock ;
  rdfs:range xsd:dateTime ;
  rdfs:label "Expiration Time" ;
  rdfs:comment "When the lock will expire if not renewed" .

lock:blockedBy a rdf:Property ;
  rdfs:domain lock:Lock ;
  rdfs:range lock:Lock ;
  rdfs:label "Blocked By" ;
  rdfs:comment "Lock that is blocking this one (for deadlock detection)" .

lock:priority a rdf:Property ;
  rdfs:domain lock:Lock ;
  rdfs:range xsd:integer ;
  rdfs:label "Priority" ;
  rdfs:comment "Lock priority (higher = more important)" .

lock:fingerprint a rdf:Property ;
  rdfs:domain lock:Lock ;
  rdfs:range xsd:string ;
  rdfs:label "Fingerprint" ;
  rdfs:comment "Process fingerprint for validation" .

# Lock states
lock:Active a lock:LockState ;
  rdfs:label "Active" ;
  rdfs:comment "Lock is currently held and valid" .

lock:Expired a lock:LockState ;
  rdfs:label "Expired" ;
  rdfs:comment "Lock has expired and should be cleaned up" .

lock:Released a lock:LockState ;
  rdfs:label "Released" ;
  rdfs:comment "Lock has been explicitly released" .
```

## Week 2: RDF Lock Manager Implementation

### Task 2.1: Create RDF LockManager (Days 5-7)

**File:** `src/git-native/RDFLockManager.mjs`

**Key Methods:**

```javascript
class RDFLockManager {
  // Initialize with KnowledgeSubstrate
  async initialize(knowledgeSubstrate, options = {})

  // Acquire lock with semantic deadlock detection
  async acquireLock(lockName, options = {})

  // Release lock and update RDF
  async releaseLock(lockName)

  // Query: Find circular dependencies (deadlocks)
  async detectDeadlocks() → SPARQL ASK query

  // Query: All locks blocking resource X
  async getBlockingLocks(resourceId) → SPARQL SELECT query

  // Query: Abnormally long locks
  async getAbnormallyLongLocks(maxDurationMs) → SPARQL query

  // Get lock info with RDF enrichment
  async getLockInfo(lockName)

  // List all locks with graph structure
  async listLocks()

  // Cleanup expired locks
  async cleanupExpiredLocks()
}
```

**SPARQL Queries to Implement:**

1. **Deadlock Detection (ASK)**
```sparql
ASK WHERE {
  ?lock1 lock:blockedBy ?lock2 .
  ?lock2 lock:blockedBy+ ?lock1 .
}
```

2. **Locks Blocking Resource (SELECT)**
```sparql
SELECT ?lock ?owner ?duration WHERE {
  ?lock lock:resourceId ?resource ;
        lock:owner ?owner ;
        lock:acquiredAt ?acquiredAt .
  BIND((NOW() - ?acquiredAt) AS ?duration)
  FILTER(?resource = <resource://%s>)
}
ORDER BY DESC(?duration)
```

3. **Long-Running Locks (SELECT)**
```sparql
SELECT ?lock ?duration WHERE {
  ?lock lock:acquiredAt ?acquiredAt ;
        lock:expiresAt ?expiresAt .
  BIND((?expiresAt - ?acquiredAt) AS ?duration)
  FILTER(?duration > %d)  # Max duration in ms
}
```

**Implementation Notes:**
- Use KnowledgeSubstrateCore for RDF storage and transactions
- Maintain backward compatibility: still use Git refs for durability
- RDF is "read" side; Git is "write" side (event sourcing pattern)
- Transactional: lock operations are atomic via Knowledge Substrate

**Deliverables:**
- ✓ RDFLockManager.mjs (250 lines)
- ✓ SPARQL query library (80 lines)
- ✓ 15+ unit tests with SPARQL validation
- ✓ Integration tests with current LockManager

### Task 3.1: Create RDF SnapshotStore (Days 8-10)

**Key Enhancement:**

**SPARQL Queries:**

1. **Snapshot Lineage (DESCRIBE)**
```sparql
DESCRIBE ?snapshot WHERE {
  ?snapshot snap:key "workflow-state" ;
           prov:wasGeneratedBy ?operation ;
           prov:wasAttributedTo ?user ;
           snap:previousSnapshot* ?earlier .
}
```

2. **Snapshot Timeline (SELECT)**
```sparql
SELECT ?timestamp ?operation ?content WHERE {
  ?snapshot snap:key ?key ;
           snap:timestamp ?timestamp ;
           prov:wasGeneratedBy ?operation ;
           snap:contentHash ?content .
  FILTER(?key = "workflow-state")
}
ORDER BY DESC(?timestamp)
```

### Task 3.2: Create RDF QueueManager (Days 9-11)

**File:** `src/git-native/RDFQueueManager.mjs`

**Key Features:**
- Represent jobs as RDF with dependencies
- Use SPARQL for topological sort
- Detect and prevent circular dependencies
- Track job lineage

**SPARQL Queries:**

1. **Topological Sort (SELECT)**
```sparql
SELECT ?job WHERE {
  ?job a queue:Job ;
       queue:status queue:Pending .
  OPTIONAL { ?job queue:dependsOn ?dep }
  FILTER(NOT EXISTS { ?dep queue:status [ ] })
}
ORDER BY ?job
```

2. **Circular Dependencies (ASK)**
```sparql
ASK WHERE {
  ?job1 queue:dependsOn ?job2 .
  ?job2 queue:dependsOn+ ?job1 .
}
```

3. **Critical Path (SELECT)**
```sparql
SELECT ?job ?depth WHERE {
  ?job queue:dependsOn* [] .
  BIND(COUNT(DISTINCT ?dep) AS ?depth)
}
```

### Task 4.2: Migration Path & Adapter (Days 13-14)

**File:** `src/git-native/RDFLockManagerAdapter.mjs`

**Purpose:** Bridge between old JSON-based and new RDF-based implementations

```javascript
class RDFLockManagerAdapter extends LockManager {
  // Override acquireLock to write both JSON (for compatibility) and RDF
  async acquireLock(lockName, options = {}) {
    const rdfResult = await this.rdfManager.acquireLock(lockName, options);
    const jsonResult = await super.acquireLock(lockName, options);
    return rdfResult && jsonResult;
  }

  // Read from RDF, fall back to JSON
  async getLockInfo(lockName) {
    try {
      return await this.rdfManager.getLockInfo(lockName);
    } catch (e) {
      return await super.getLockInfo(lockName);
    }
  }
}
```

**Migration Strategy:**
1. Phase 1.1 (Week 2): Deploy RDF alongside JSON (read/write both)
2. Phase 1.2 (Week 3): Monitor RDF correctness vs JSON
3. Phase 1.3 (Week 4): Switch reads to RDF primarily
4. Phase 1.4 (Post): Remove JSON dependency

## Risk Mitigation

### Risk: RDF Performance Overhead
**Mitigation:**
- Use caching layer (L1: 50 queries, L2: 200 results, Disk: 100MB)
- Pre-compile SPARQL queries
- Benchmark before/after each week
- Fallback to JSON if SPARQL queries timeout

### Risk: Backward Compatibility
**Mitigation:**
- Keep JSON writes alongside RDF for 2 weeks
- Feature flag to disable RDF if issues arise
- Comprehensive integration tests

### Risk: Complexity Increase
**Mitigation:**
- RDF is "read" side only; Git remains "write" side
- Clear separation of concerns in code
- Well-documented query patterns
- Reusable query library
